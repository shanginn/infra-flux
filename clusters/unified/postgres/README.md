# PostgreSQL: эксплуатация

В Git все три StatefulSet имеют `replicas: 0`. Подготовка каталога и секретов
не запускает PostgreSQL. Отдельная Flux Kustomization создаётся только через
`bootstrap/ansible/postgres-activate.yml` с приватными переменными и явным
выбором режима fencing. Корневые конфигурации прежних кластеров не меняются.

## Запуск и подключение

Сначала `postgres-prepare.yml` проверяет идентичность кластера, три Ready-ноды,
свободное место и создаёт один набор credentials/CA с копиями на всех нодах.
`/etc/infra-postgres/runtime.json` содержит секреты; хранить его только на
серверах и в зашифрованной резервной копии, никогда в Git.

Первый этап активации — `bootstrap-home`: один новый пустой primary дома.
После успешного `/opt/infra/verify-runtime.py` внутри его контейнера этап `full`
добавляет Москву и Финляндию. Проверить одну primary и две streaming async-реплики,
одинаковый system identifier, TLS и восстановление резервной копии до переноса
приложений. Отсутствующий контроллер с непустыми данными требует отдельного
восстановления; обычный bootstrap откажется их принимать.

Приложения используют `unified-postgres.database.svc:5432` для записи и
`unified-postgres-replicas.database.svc:5432` для чтения с допустимым отставанием.
Клиентскому namespace нужна метка `infra.shanginn.io/postgresql-client=true`.
Использовать отдельные роли приложений, `sslmode=verify-full` и сохранённый CA.
Пароли суперпользователя и replication-ролей приложениям не выдаются.
PostgreSQL не публикуется через ingress, NodePort или публичный адрес.

### Бюджет подключений

Начальная конфигурация допускает 200 подключений, из них 3 зарезервированы
для суперпользователя. До запуска приложений задать явные пределы их пулов:
учитывать каждый процесс, каждый экземпляр и отдельные пулы одного сервиса.
Планировать не более 176 одновременно открытых обычных подключений, включая
Patroni, мониторинг и фоновые задания; оставшиеся 21 — запас для эксплуатации.
Этот бюджет необходимо обеспечить настройками клиентов: серверный лимит сам
по себе не ограничивает отдельные приложения.

Сохранять `shared_buffers=512MB`, `work_mem=4MB` и
`maintenance_work_mem=128MB`. `work_mem` выделяется отдельным операциям запроса,
а не один раз на соединение; лимит контейнера 3Gi не гарантирует выполнение
200 тяжёлых запросов одновременно. При переносе наблюдать память, активные
запросы, ожидания подключения и отставание реплик; настройки старого сервера
с большим объёмом RAM не переносить целиком.

Раздел `bootstrap.dcs` действует при создании кластера. Изменение этого YAML
не меняет лимит уже работающего PostgreSQL. Для существующего кластера изменить
только `postgresql.parameters.max_connections` через Patroni `/config`, затем
при увеличении лимита перезапустить PostgreSQL на репликах по одной и primary
последним. Использовать Patroni `/restart`, проверяя роль и `pending_restart`;
не перезапускать для этого Patroni, Pod или сервер. Перед каждым следующим
шагом проверить новую настройку, Ready и применение WAL; primary должен
остаться дома. Если ответ на изменение потерян, сначала прочитать фактическое
состояние и журнал операции, не отправлять запрос повторно.

`bootstrap/ansible/postgres-capacity.yml` автоматизирует именно переход
100 → 200. По умолчанию он выполняет только `inspect`; его результат `review`
и идентификатор кластера сохраняются в приватных переменных. Для изменения
нужны `postgres_capacity_enabled: true`, один `postgres_capacity_operation`
(32 шестнадцатеричных символа) и этот неизменный `postgres_capacity_review`.
Выполнять отдельные действия `patch`, `restart-msk`, `restart-fin`,
`restart-home` строго по порядку. Каждое проверяет предыдущий результат,
идентичности, настройки и репликацию. Журнал хранится на управляющей ноде в
`/etc/infra-postgres/capacity-100-to-200` с правами root; туда же попадает
ограниченный диагностический вывод. `readback` только читает состояние и не
продолжает незавершённое действие. Не удалять журнал ради повторного запуска.

Источники: [Patroni: изменение общей памяти](https://patroni.readthedocs.io/en/latest/patroni_configuration.html#postgresql-parameters-that-touch-shared-memory),
[PostgreSQL: подключения](https://www.postgresql.org/docs/18/runtime-config-connection.html),
[PostgreSQL: память запросов](https://www.postgresql.org/docs/18/runtime-config-resource.html).

Для административной проверки сначала получить текущий primary:

```sh
kubectl -n database get pods -l cluster-name=unified-postgres -L role
kubectl -n database exec PRIMARY_POD -c postgres -- /opt/patroni/bin/python /opt/infra/verify-runtime.py
kubectl -n database exec -it PRIMARY_POD -c postgres -- psql -h /run/postgresql -U postgres -d postgres
```

## Переключение и пределы защиты

Режим `watchdog` требует отдельного согласия на возможный перезапуск всей
машины и privileged-контейнер. Подготовка `postgres-watchdog.yml` только
загружает отдельный `softdog`; Patroni вооружает его при получении primary.
Таймер — 30 секунд, DCS TTL — 60, HA loop и retry timeout — по 5 секунд.
Без работоспособного watchdog нода не должна становиться primary.

На доме аппаратный iTCO и существующий `watchdog.service` остаются отдельными:
Patroni использует `/dev/patroni-watchdog`, указывающий на Software Watchdog.
Legacy `/dev/watchdog` относится к `watchdog0`; его не открывать и не отдавать
Patroni. Нельзя останавливать существующую watchdog-службу или переносить её
устройство в контейнер.

При потере DCS Patroni сначала останавливает PostgreSQL. Если процесс завис,
software watchdog может перезапустить весь сервер, включая etcd, приложения
и вычисления GPU. Это зависит от работающих таймеров ядра и механизма reboot.
Пауза VM, suspend, зависание ядра, отказ reboot, большой скачок часов или
вмешательство root требуют внешнего fencing. `patronictl pause` отключает
watchdog-защиту и для этого режима запрещён. TTL не является обещанием RTO.

В режиме `manual-verified-off` watchdog выключен, а автоматическое повышение
реплики запрещает `pre_promote`. Оператор сначала подтверждает выключение
прежнего primary и исключает его самопроизвольный запуск. Недоступность ping,
SSH, удаление Pod или drain этого не доказывают. Только после этого создаётся
одноразовое разрешение по `manual-promotion-approval.example.yaml` для точных
имени и UID кандидата, сроком не более 60 секунд. Пример сам по себе не
разрешает повышение. Смена режима живого кластера требует отдельной процедуры.

Плановый switchover выполнять через Patroni после проверки репликации; прямой
`pg_ctl promote` обходит fencing и не используется. При сомнении о состоянии
старого primary сохранить отказ записи до подтверждённого fencing.

Предпочтительный primary — дом. `failover_priority`: home 100, msk 50, fin 10.
При равном полученном WAL выбирается больший приоритет; более актуальная
реплика имеет преимущество независимо от приоритета. Это не автоматический
failback: восстановившийся дом сначала возвращается репликой. После проверки
трёх Ready-экземпляров, TLS, streaming и достижения домашней репликой снятого
с текущего primary WAL LSN оператор выполняет Patroni switchover с явным
кандидатом `unified-pg-home-0`, затем проверяет одну primary и две async-реплики.
Действующий кластер остаётся на этапе `full`; `bootstrap-home` предназначен
только для пустой установки, не для переноса роли или восстановления.

StatefulSet использует `OnDelete`: обновление приоритетов в Git не перезапускает
работающие Pod; перезапуск контейнера внутри прежнего Pod сохраняет старый env.
Для изменения приоритетов сначала по одной заменить реплики из нового template,
каждый раз дожидаясь Ready и catchup. Затем планово переключить primary на уже
обновлённую VPS, заменить домашний Pod как реплику, дождаться catchup и штатно
вернуть primary домой. Никогда не заменять два участника одновременно.
После этого `postgres-priority.yml` с явным включением
применяет только `tags.failover_priority` в локальной конфигурации через Patroni
reload и проверяет неизменность роли и времени запуска PostgreSQL. Новый Pod
получает приоритет из декларативного environment. Старый Pod env блокирует reload;
playbook не переключает primary и не заменяет Pod.

Репликация асинхронная: COMMIT не ждёт удалённые реплики. Последние
подтверждённые транзакции могут потеряться. Порог кандидата 16MiB сравнивается
с известным Patroni LSN и **не ограничивает полную потерю 16MiB**: новые записи
после последнего наблюдения также могут отсутствовать. Разделение без
доступного большинства DCS приводит к отказу записи, а не к независимым primary.

## Место и WAL

На каждой ноде выделен плановый бюджет 24Gi для PostgreSQL; local PV не
устанавливает файловую квоту. Подготовка и активация проверяют оставшееся место
с учётом других заданных резервов. Предупреждения роста нужны до заполнения
диска: данные 18/21Gi, WAL 6/8Gi. Сборщик включается отдельно через
`postgres-monitoring.yml` после запуска базы; ошибка сбора не считается успехом.

`max_slot_wal_keep_size=8GB` и `max_wal_size=2GB` не являются жёсткими
пределами диска: checkpoint и другие удерживающие WAL условия могут вызвать
превышение. Отслеживать `wal_status`, `safe_wal_size`, отставание и свободный диск.
Отсутствующий участник теряет slot после `member_slots_ttl=5min`; при утрате
нужного WAL потребуется полная пересборка реплики с primary. Перед `patronictl
reinit` подтвердить точное имя реплики, отсутствие роли primary, достаточное
место и разрешение на замену её данных. Не удалять `pg_wal` вручную.

## Резервные копии и восстановление

`archive_mode=off`: потоковый логический экспорт не даёт PITR. Реплики и WAL
slots не заменяют резервные копии. PostgreSQL job на Mac включается только
после проверки настоящего экспорта и восстановления; до этого нельзя заявлять
наличие резервной копии рабочих БД.

`bootstrap/macos/export-postgres.py` передаёт `pg_dumpall` напрямую в restic
без полного архива на VPS. Это согласованный снимок **каждой БД отдельно**,
не общий момент всех БД. Экспорт включает роли и их password hashes, поэтому
поток должен сразу попадать в шифрованный репозиторий. Смена primary или
инвентаря БД/ролей во время экспорта отменяет копию.

`verify-postgres.py` проверяет формат, размер, SHA-256 и завершённость потока,
затем восстанавливает SQL в отдельный временный PG18 на доме: без host network,
production volumes и credentials, с лимитами CPU/RAM и контролем места.
Проверяются выполнение SQL, состав БД/ролей и `pg_amcheck`. Проверочный SQL
временно существует только в приватном каталоге Mac; удаляется после проверки.
Тег `verified` допустим только после успешного восстановления и уборки scratch.
Проверка SQL не заменяет прикладные проверки восстановленных сервисов.

При настоящем восстановлении сначала изолировать прежние primary и запись
приложений. Выбрать проверенный snapshot; восстановить исходный bundle CA и
credentials. Логический SQL загружать только в новый изолированный PG18,
инициализированный с отдельным bootstrap superuser, чтобы роли из dumpall не
конфликтовали. Проверить данные, права и расширения; затем отдельной процедурой
сформировать один Patroni primary и заново создать две реплики. Не поднимать
три независимо восстановленных writable-копии и не удалять DCS вслепую.

Для физического backup всей инсталляции потребуется отдельный `pg_basebackup`
клиент на Mac с `-X stream`, сохранением в локальное защищённое staging и
`pg_verifybackup` плюс тестовый запуск совместимого PG18/Linux. `-D -` нельзя
совмещать с `-X stream`. Непрерывный PITR требует отдельного WAL-архива, который
работает и при выключенном Mac; он этим набором файлов не настроен.

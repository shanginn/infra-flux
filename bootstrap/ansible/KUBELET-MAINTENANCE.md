# Kubelet: локальный отказоустойчивый API

`kubelet-endpoint-maintenance.yml` меняет только `server` в существующем
`/etc/kubernetes/kubelet.conf` на `https://api.unified.internal:7443`.
Этот адрес ведёт на уже установленный HAProxy каждой машины. CA, контекст,
клиентский сертификат, путь ротации ключа и исходный bootstrap marker сохраняются.
Оригинал файла и журнал операции остаются у root в каталоге
`/etc/infra-flux/kubelet-endpoint-maintenance`, права 0700/0600.

Сначала запустить playbook с обычным приватным inventory без apply. Он не пишет
файлы и проверяет три Ready-ноды, три API, три участника etcd, одинаковую
версию v1.36.5, локальное разрешение имени, TLS и чтение собственной Node/Lease
с действующими учётными данными kubelet. Для применения передать вне Git
`kubelet_endpoint_apply: true` и `kubelet_endpoint_expected_config_sha256`
с тремя проверенными хешами `home`, `msk`, `fin` из inspect. Также передать
`kubelet_endpoint_expected_identity` с теми же ключами и полями `node`,
`node_uid`, `machine_id`, `ca_sha256`, `bootstrap_sha256` каждого узла.
Адрес, уже изменённый без собственного журнала, автоматически не принимается.

Применение последовательное, под общей CAS-блокировкой испытаний. Для каждого
узла фиксируются исходные процессы контейнеров и kubelet. Единственная команда
управления сервисами — неблокирующий `restart kubelet.service`, отправка ограничена
8 секундами. Контейнеры, containerd, API proxy и manifests не перезапускаются
командами обслуживания. Успех требует нового процесса kubelet, последующего
продления той же NodeLease, сохранения процессов всех исходно работавших
контейнеров и 30 секунд полного здоровья трёх узлов/API/etcd.

Если отправка restart оборвалась или результат неясен, намерение уже записано.
Повторный запуск только наблюдает PID/Lease и **не отправляет restart повторно**.
Неподтверждённое восстановление удерживает общую блокировку; нельзя запускать
следующий узел или испытание. Если процесс не сменился, хост перезагрузился,
контейнер завершился либо файл изменён извне, сначала разобрать состояние и
проверить частный журнал. Автоматического отката и сброса блокировки нет.
Частично созданный каталог без полного журнала также требует ручной проверки.

После kubeadm upgrade проверить endpoint заново: kubeadm может переписать
kubelet.conf. Завершённая запись обслуживания не принимает новое содержимое
автоматически: для новой операции сначала независимо проверить upgrade,
сохранить предыдущий частный журнал и согласовать новую generation.
Нельзя отключать несуществующим feature gate выбор локального API kubeadm.
Перед обновлением kubelet проверить версии **всех** backend API: при балансировке
kubelet не должен быть новее самого старого из них. Текущий helper намеренно
отклоняет смешанные версии; изменение VERSION требует отдельного ревью.

Общие atomic I/O, CAS lock и etcd health берутся из соседнего
`files/etcd-probe-maintenance.py` только при совпадении встроенного SHA256.
Изменение общего helper требует повторного ревью и обновления этого pin.

Основания: [реализация kubeadm join](https://github.com/kubernetes/kubernetes/blob/master/cmd/kubeadm/app/cmd/phases/join/kubelet.go),
[upstream issue о синхронном удалении mirror Pod при недоступном локальном API](https://github.com/kubernetes/kubernetes/issues/139502),
[официальная политика version skew](https://kubernetes.io/releases/version-skew-policy/).
Issue описывает возможный механизм задержки и не доказывает единственную причину
любого конкретного сбоя загрузки.
